# MetaCoOc data-release checklist

This maintainer-only file is not part of the rendered documentation. Use it
for every new MetaCoOc scientific data release or revision.

## 1. Fix the release identities

- [ ] Record the package commit and environment used to generate the data.
- [ ] Choose the base release, variant, and revision identifiers using
      `R<release>_<gtdb|globdb>_rev<n>`.
- [ ] Increment the revision if any scientific input changes. Do not replace
      artifacts belonging to an existing revision.
- [ ] Confirm the Ingredients `format_version`. Change it only for an on-disk
      schema change, not for a new scientific dataset.
- [ ] Keep the package version, data release, and `format_version` recorded as
      three separate identities.
- [ ] Freeze the source taxonomic profiles, SRA metadata, biome mapping, and
      generation parameters. Record their locations, versions, and checksums.

A revision is complete: a changed scientific input requires new raw and
aggregated Ingredients for both GTDB and GlobDB, together with new shared
support artifacts under the same revision.

## 2. Generate the complete snapshot

- [ ] Prepare the GTDB and GlobDB taxonomic profile TSVs with `sample`,
      `taxonomy`, and `coverage` columns.
- [ ] Prepare the shared sample-to-biome TSV with `accession`, `level_1`, and
      `level_2` columns.
- [ ] Prepare the shared SRA metadata TSV and confirm that sample identifiers
      match the profiles.
- [ ] Generate raw and aggregated Ingredients for each variant. The command
      template is:

  ```bash
  metacooc format \
    --tax_profile <variant-profile.tsv> \
    --sample_to_biome_file <sample-to-biome.tsv> \
    --output_dir <staging-directory> \
    --aggregated \
    --archive_ingredients \
    --data_release R<release>_<variant>_rev<n>
  ```

- [ ] Confirm that every Ingredients manifest records the intended
      `data_release`, integer `format_version`, generation date, matrix shapes,
      dtypes, aggregation state, and deterministic component filenames.
- [ ] Confirm that biome mappings are embedded in every Ingredients directory.
- [ ] Compress the shared support files with their deterministic official
      names:
  - `sample_to_biome_R<release>_rev<n>.tsv.gz`
  - `sra_metadata_R<release>_rev<n>.tsv.gz`

## 3. Validate the staged data

- [ ] Load every raw and aggregated Ingredients directory through
      `load_ingredients`; do not validate only the source TSVs.
- [ ] Confirm that matrices remain sparse and coverage and presence matrices
      are loaded lazily from disk.
- [ ] Compare sample sets across GTDB, GlobDB, biome mappings, and metadata.
      Explain and record any intentional differences.
- [ ] Record, for each variant, the sample count, original taxon count,
      species count, aggregated-row count, matrix shapes, and non-zero counts.
- [ ] Check representative taxa at species and higher ranks. Confirm that raw
      rows retain unfilled profile coverage and `AGGREGATED` rows sum the
      intended descendants without changing the original rows.
- [ ] Check representative biome, metadata, taxa-context, and focal-taxa
      searches before publication.
- [ ] Run focused format, registry, download, search, and pipeline tests, then
      run the complete test suite with `uv run pytest -q`.

## 4. Freeze and publish the artifacts

- [ ] Treat the final archives as publication candidates. Once their checksums
      are recorded, do not regenerate them under the same revision.
- [ ] Calculate SHA-256 checksums for all six required artifact classes:
  - GTDB raw Ingredients archive;
  - GTDB aggregated Ingredients archive;
  - GlobDB raw Ingredients archive;
  - GlobDB aggregated Ingredients archive;
  - shared sample-to-biome TSV archive;
  - shared SRA metadata TSV archive.
- [ ] Upload the exact final bytes to a Zenodo draft using the deterministic
      filenames required by `validate_registry`.
- [ ] Download each draft artifact independently and confirm its filename,
      size, and SHA-256 checksum before publishing the Zenodo record.
- [ ] Record the immutable Zenodo record ID or IDs. Publish only after the
      complete revision has passed validation.

If a published artifact is scientifically or structurally wrong, issue a new
revision. Do not replace the registry checksum or file behind an existing
release identity.

## 5. Update and validate the registry

- [ ] Add the new revision to `metacooc/data_registry.v1.json` without changing
      older revision entries.
- [ ] Record every exact filename, lowercase SHA-256 checksum, and Zenodo
      record ID.
- [ ] Set the base release's `current_revision` to the new revision.
- [ ] Set `default_data_release` to the latest GlobDB revision when this is the
      new registry default.
- [ ] Update the registry date.
- [ ] Run the registry tests and confirm that `validate_registry` accepts the
      complete file.
- [ ] Confirm that the same registry is available from the package and the
      configured `main`-branch registry URL.

## 6. Test published downloads

- [ ] In an empty data directory, list releases with
      `metacooc download --list_data_releases` and check the current/default
      markers.
- [ ] Download the exact GTDB release and confirm raw and aggregated
      Ingredients extraction and manifest identity.
- [ ] Download the exact GlobDB release and perform the same checks.
- [ ] Repeat one download with `--include_metadata`; confirm that metadata is
      optional and is not fetched by an ordinary download.
- [ ] Confirm that checksum failures remove temporary files and do not leave a
      partially installed release.
- [ ] Run an analysis without `--data_release` and confirm that the CLI reports
      and uses the intended registry default.

## 7. Refresh documentation and examples

- [ ] Update the archive-scale metagenome and species counts on the landing
      page and introduction. Record the count source and date in the release
      record.
- [ ] Search the repository for the previous release identifier and update
      pinned documentation commands, README examples, and maintained scripts
      where the new release should be demonstrated.
- [ ] Review taxonomy-sensitive wording and focal taxa for name changes between
      releases.
- [ ] Rerun the maintained bee-gut, human-gut, and *Methanocatella smithii*
      workflows against the new release.
- [ ] Inspect summary and detailed outputs, then regenerate the three example
      plots only after confirming that the workflows still answer the intended
      biological questions.
- [ ] Build the documentation with warnings as errors and run link checking.
- [ ] Confirm that installation commands, data links, Zenodo references, CLI
      options, and example output filenames remain accurate.

## 8. Close the release

- [ ] Review the complete registry and documentation diff separately from any
      package-version release work.
- [ ] Preserve the frozen inputs, commands, logs, validation summaries,
      checksums, Zenodo record IDs, and published registry in the release
      record.
- [ ] Confirm that a clean installation can resolve, download, load, and run a
      small analysis with the new default release.
- [ ] Announce the exact data release identity. Mention the package version
      separately when a new software release is also required.
